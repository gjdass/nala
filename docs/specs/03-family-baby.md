# 03 — Family & baby profile

Status: done

## Goal

Let several households share one Nala instance, each one private: the instance admin invites someone to create their family, members invite their caregivers, the family admin removes them when needed, and members register the babies they track, with a quick way to switch between babies, across families.

## Decisions

- **Families on one instance.** An instance hosts any number of families, isolated from each other. A family has a name and its members; a person can belong to several families (one membership per family). Each family has exactly one **family admin**: the person who created it. There is no admin handover (feature list, idea), and the family admin can't be removed. The **instance admin** (02) is a separate, account-level role: they invite people to create a family and manage accounts, and see no family data; they belong to their own family like everyone else.
- **Members are equal, except for destructive actions.** Every member of a family can log and edit its entries, add and edit its babies, and invite people into it. Only the family admin can rename the family, delete a baby or remove a member.
- **Family isolation:** a user only reaches the families they belong to, and those families' babies, entries, members and invitations. Anything else answers exactly as if it didn't exist: the same 404 and code as an unknown id (`familyNotFound`, `babyNotFound`, `<entry>NotFound`, `invitationUnknown`), checked before any role check, so no answer tells whether another family's id exists. One shared Core check (`Nala.Core/Families`) resolves a family, a baby or an entry's baby to the caller's membership (and role); every family, baby, activity, History, Trends and live endpoint goes through it, none rebuilds it. The instance admin gets nothing more than any user.
- **Creating a family:** only at first-run setup (02) and by accepting a new-family invitation from the instance admin (02). The family is created when the invitation is accepted, never when it is sent, with the name typed then; the person becomes its admin and only member. It has no baby yet: home shows the add-a-baby empty state.
- **Family name:** trimmed, 1–50 characters; validation codes `required` / `tooLong` (field `familyName` at setup and invitation acceptance, `name` on rename). The family admin can rename it.
- **Family endpoints:** `GET /api/families` → 200 `[{ id, name, isAdmin }]`, the caller's families, by name (case-insensitive), then by creation. `PATCH /api/families/{id}` with `{ name }` → 200 with the family; errors, in this order: 404 `{ code: "familyNotFound" }` for a family the caller isn't in; 403 `{ code: "familyAdminOnly" }` for a member who isn't its admin; 400 validation problem. After a rename the web reloads the families, so the top app bar, the switcher and the families order follow.
- **Current family on the device:** the device remembers the selected family and the selected baby in it (per device, not per account, in `localStorage`). Picking a baby selects its family. On load, a remembered family the user is no longer in falls back to the first family (families order), and a remembered baby that no longer exists to its family's first baby. The settings' family sections, invitations and new babies are for the current family.
- **Baby endpoints:** `GET /api/babies` → 200 `[baby]`, the babies of every family of the caller, oldest birth date first, then by creation. `POST /api/babies` with `{ familyId, name, birthDate, sex?, birthWeightG?, birthLengthCm?, birthHeadCircumferenceCm? }` → 201 with the baby; 404 `{ code: "familyNotFound" }`; 400 validation problem otherwise. A baby is `{ id, familyId, name, birthDate: "yyyy-MM-dd", sex: "girl" | "boy" | "unspecified", birthWeightG, birthLengthCm, birthHeadCircumferenceCm }`; the id is generated by the server (babies are not queued offline). `PUT /api/babies/{id}` with the same body without `familyId` replaces every field (an omitted sex or measurement is reset to unspecified / cleared); a baby never changes family → 200 with the baby; 400 validation problem; 404 `{ code: "babyNotFound" }`. Any member of the baby's family.
- **Baby validation codes:** `familyId`: `required` (create only); `name`: `required` / `tooLong` (trimmed); `birthDate`: `required` / `inFuture`; `sex`: `invalid` (omitted = `unspecified`); `birthWeightG`: `outOfRange`, `invalid` when not whole grams; `birthLengthCm` / `birthHeadCircumferenceCm`: `outOfRange`, `invalid` with more than one decimal. The web shows `babies.errors.<field>.<code>`. Same rules in `Nala.Core/Babies/BabyFields` and the web's `nala-baby-form`.
- **Age display:** from the birth date to the device's local today, by calendar day. Under 14 days: days ("0 days" on the day of birth). From 14 days until the 3-month anniversary: weeks + days. From then on: months + days, still in months after the first year ("14 months 3 days"). A monthly anniversary falling on a day the month doesn't have is its last day. A zero part is left out ("2 weeks", "4 months"). Singular/plural per language. Shared web `BabyAgePipe` (keys `babies.age.<unit>.<one|other>`).
- **"Not in the future":** the API refuses a birth date after today in UTC+14 (the latest calendar date anywhere), so no device's local today is refused; the web form caps it at the device's local today.
- **Baby form:** the shared `nala-baby-form` in a form sheet: a bottom sheet on phones, a dialog on wide screens (the shared `SheetService`, like 04's entry sheet), with the shared `nala-sheet-header` (×, title, Save). Save is disabled while the form is invalid; × asks before discarding changes; tapping outside the sheet or Escape discards them and closes it without asking (spec 04). The birth date is picked from the calendar (field read-only, opens it on tap), in the app's language. A new baby goes to the current family.
- **Deleting a baby:** `DELETE /api/babies/{id}` → 204; 404 `{ code: "babyNotFound" }` (unknown, or outside the caller's families, checked first); 403 `{ code: "familyAdminOnly" }` for a member who isn't the family admin. The family admin finds Delete at the bottom of the baby edit sheet (hidden from other members and when adding). It opens the shared `nala-type-to-confirm-dialog`: Delete stays disabled until the baby's name is typed, matched with surrounding spaces ignored and case kept. The sheet then closes with the deleted id; the device's selection falls back to the family's first baby. Each activity table references the baby with `ON DELETE CASCADE`, tested by its own spec.
- **Two kinds of invitation**, with the token scheme, single use, 7-day expiry and revoke rules of 02: a **join invitation** adds a member to one family (any of its members creates it); a **new-family invitation** lets its recipient create a family (instance admin only, endpoints in 02). An invitation stores its family for a join invitation, none for a new-family one.
- **Join invitation endpoints:** any member of the family; 404 `{ code: "familyNotFound" }` for a family the caller isn't in. `POST /api/families/{familyId}/invitations` → 200 `{ token, expiresAt }` (7 days); the web builds `/invite/{token}` from its own origin. `GET /api/families/{familyId}/invitations` → 200 `[{ id, createdBy, createdAt, expiresAt }]` (`createdBy` is the creator's display name), that family's pending invitations only (unused, unexpired, unrevoked), newest first. `POST /api/families/{familyId}/invitations/{id}/revoke` → 204 for a pending or already revoked invitation (idempotent); 410 `{ code }` with `invitationUsed` or `invitationExpired`; 404 `{ code: "invitationUnknown" }`, also for another family's invitation. Revoking is a conditional update, so a revoke and an acceptance racing on one link can't both succeed.
- **Join invitation by email:** `POST /api/families/{familyId}/invitations/email` with `{ email }` → 202 `{ expiresAt }`: creates a join invitation as above and queues an email with its link through `IEmailOutbox`. 404 `{ code: "emailInviteDisabled" }` when SMTP is off (checked first, after the family); 400 validation problem `email`: `required` / `invalid` (rule of 02) / `alreadyMember` (a non-deleted member of that family has it). An email with an account elsewhere is fine: that person signs in and accepts (02). The address is only used for sending, never stored: the invitation is an ordinary one (pending list, revoke, acceptance by any account). The email is plain text in the inviter's language (EN/FR, else English): subject "You're invited to Nala" / "Invitation à rejoindre Nala", who invites them to which family, the link `{NALA_PUBLIC_URL}/invite/{token}`, that it works once until its expiry (UTC), and to ignore it if they don't know the sender.
- **Joining:** accepting a join invitation, through registration or with an existing account (02), adds a member membership. Someone already in the family is refused (409 `{ code: "alreadyMember" }`) and the invitation stays unused.
- **Invitations in settings:** the Members & invitations section (current family) has an Invite button, which creates a link and opens the shared `nala-share-link-dialog` (link, expiry, Copy, Share); with `smtpEnabled`, an outlined "Invite by email" button next to it opens a dialog (email field, Cancel / Send; errors under the field, the dialog stays open), which closes on success with a snackbar "Invitation sent to {email}" and reloads the list. Then the pending list, one shared `nala-invitation-list-item` each ("Invited by {name}", "Expires {date and time}") with a Revoke text button. Revoke is immediate (a new link is easy to make), confirmed with a snackbar. With none pending, the list says so.
- **Member endpoints:** `GET /api/families/{familyId}/members` → 200 `[{ id, displayName, email, isAdmin }]` (`isAdmin`: family admin): the family's non-deleted members, the admin first then by display name (case-insensitive); any member. `POST /api/families/{familyId}/members/{userId}/remove` → 204: deletes the membership. Errors, in this order: 404 `{ code: "familyNotFound" }`; 403 `{ code: "familyAdminOnly" }` for anyone but the family admin; 404 `{ code: "userNotFound" }` for someone not in the family (already removed included); 403 `{ code: "adminCannotRemove" }` for the admin themselves. The removed person's account, sessions and other families are untouched; the invitations they created for this family that are still pending are revoked; their entries are kept.
- **Members in settings:** the Members & invitations section starts with a "Members" heading and one shared `nala-member-list-item` per member (name, email, admin badge). The family admin sees a Remove text button on every row but their own; it asks for confirmation in the shared `nala-confirm-dialog`, then the member leaves the list and a snackbar confirms ("{name} was removed"). Removing reloads the members and pending invitations lists.
- **Family in settings:** a Family section first, with the current family's name; the family admin sees a Rename text button opening a dialog (the shared family name field, filled with the current name; Cancel / Save; errors under the field, the dialog stays open), confirmed with a snackbar "Family renamed". Then Babies and Members & invitations, both for that family.
- **Family admin deleting their account** (02): every family they administer is deleted, with its babies (and so every entry of those babies), its memberships and its invitations. The other members keep their accounts and their other families; devices showing a deleted family fall back as in Current family.
- **Baby switcher across families:** with one family, as before: hidden with one baby (or none), otherwise a menu of its babies. With several families, always available: the menu lists each family name as a heading (families order) with its babies under it (age, the selected one ticked); a family without a baby shows one "No baby yet" item, which selects that family. The top app bar shows the selected baby (name + age), or the current family's name when it has no baby.
- **No baby yet:** when the current family has no baby, home shows only the shared `nala-empty-state` ("Add a baby", opening the baby sheet for the current family) under the top app bar; settings stays reachable from the bottom navigation bar (04). History shows the same empty state (spec 11).
- **No family:** a user in no family (removed from their last one, or their last one deleted) sees, on home, History and Trends, the shared `nala-empty-state` "You're not part of a family yet. Ask a family member to invite you.", with no action and no baby switcher. Settings then shows no Family, Babies nor Members & invitations section. The instance admin always has a family (they can't be removed from it nor delete their account).
- **Live entries:** `GET /api/live` (04) only returns the live entries of babies of the caller's families; the mini-bar lists them all, each with its baby's name when the user has more than one baby.
- **Existing instances:** the migration creates one family named "Family" (the family admin can rename it), makes the instance admin its admin and every other non-deleted, enabled user a member, and puts every baby and every invitation in it. Disabled users get no membership: since disabling no longer exists (02), they can sign in again and see the no-family state until invited.

## User stories

- As the instance admin, I want to invite someone to create their own family, without seeing their data.
- As an invited person, I want to create my family and give it a name, then add our baby.
- As a member, I want to invite a caregiver into my family by sharing a link, so they can log for our baby, even if they already use Nala with another family.
- As a member, I want to see the members and pending invitations of my family, and revoke an invitation I no longer need.
- As the family admin, I want to remove someone from my family so they can no longer access our data.
- As the family admin, I want to rename my family.
- As a member, I want to add a baby with their name, birth date, sex and birth measurements.
- As a member of several families, I want to quickly switch between babies of all my families, and have the app remember which one I was looking at.
- As a member, I want to edit a baby's profile.
- As the family admin, I want to delete a baby added by mistake.

## Acceptance criteria

Each item becomes at least one test, written failing first.

### Families
- [x] The account created at first-run setup (02) is the admin of a first family, named at setup.
- [x] Accepting a new-family invitation (02) creates a family with the typed name (1–50 characters); the person is its admin and only member, and it has no baby.
- [x] A person can belong to several families, admin of some and member of others; `GET /api/families` lists theirs with their role.
- [x] Every family has exactly one admin, its creator; no action changes it.
- [x] Only the family admin can rename the family; other members don't see the action and the endpoint refuses them (403).
- [x] On an existing instance, the migration puts every baby and every non-deleted, enabled user in one family "Family", with the instance admin as its admin; disabled users get no membership.

### First baby
- [x] When the current family has no baby, the app shows an empty state inviting the user to add one to it; no activity screen is reachable until it has one.
- [x] A user in no family sees an empty state asking to be invited, with no add-a-baby action and no activity screen.

### Babies
- [x] A baby has a name (required, 1–50 characters), a birth date (required, not in the future), a sex (girl / boy / unspecified, default unspecified), and optional birth weight (g), birth length (cm) and birth head circumference (cm).
- [x] Birth measurements, when given, must be positive and within plausible bounds (weight 300–7000 g, length 20–70 cm, head circumference 15–50 cm).
- [x] Any member of a family can add a baby to it and edit any field of its babies; a baby never changes family.
- [x] The baby's age is shown from the birth date in days for the first 2 weeks, then weeks + days until 3 months, then months + days (e.g. "5 days", "6 weeks 2 days", "4 months 10 days"), in the user's language.
- [x] Only the family admin can delete a baby, after a confirmation that requires typing the baby's name. Deleting a baby deletes all of that baby's entries.
- [x] A member who isn't the family admin does not see the delete action, and the delete endpoint refuses them (403).
- [x] Babies are listed by birth date, oldest first.

### Baby switcher
- [x] With one family, the switcher is available from every main screen when it has more than one baby, and hidden otherwise.
- [x] With several families, the switcher is always available and lists the babies under their family's name; a family without a baby can be selected, and the top app bar then shows its name.
- [x] The selected family and baby are remembered per device (not per account) and restored when the app is reopened. A family the user is no longer in falls back to their first family; a baby that no longer exists, to its family's first baby.

### Invitations
- [x] Any member of a family can create a join invitation link for it (single-use, expires after 7 days — see 02) and copy or share it with the device's share sheet.
- [x] If SMTP is configured, the member can instead enter an email address and the link is sent to it. An address with an account elsewhere is accepted; one of a member of that family is refused.
- [x] Any member can list the family's pending (unused, unexpired, unrevoked) invitations with who created them and when they expire, and revoke any of them. A revoked link cannot be used. Another family's invitations are neither listed nor revocable.
- [x] Accepting a join invitation (new or existing account, 02) makes the person a member of that family; someone already in it is refused and the link stays usable.

### Members
- [x] Any member can list their family's members (display name, email, family admin badge). Deleted accounts and removed members are not listed.
- [x] Only the family admin can remove a member: the membership ends and the person loses access to that family only (their account, sessions and other families are kept); their pending invitations for that family are revoked; their entries are not changed.
- [x] A member who isn't the family admin does not see the remove action, and the endpoint refuses them (403).
- [x] The family admin cannot remove themselves. A member who wants to leave asks the family admin or deletes their account (02).
- [x] A removed member can only come back through a new join invitation.

### Family admin account deletion
- [x] A family admin deleting their account (02) deletes every family they administer, with its babies, every entry of those babies, its memberships and its invitations; the other members keep their accounts and other families, and lose access to the deleted family.
- [x] Entries the deleted person logged in families where they were a member are kept.

### Authorization and isolation
- [x] Every baby, activity, History and live endpoint only works for members of the baby's family; for anyone else, the baby or entry answers the same 404 and code as an unknown id. Each section's API tests include a user from another family.
- [x] Family, member and invitation endpoints of a family the caller isn't in answer 404 `familyNotFound`.
- [x] `GET /api/babies` and `GET /api/live` only return the babies and live entries of the caller's families.
- [x] Creating, re-sending or starting an entry with an id that belongs to another family's entry is refused with 404 and leaves that entry unchanged.
- [x] The instance admin reaches no data of a family they aren't a member of.
- [x] Family-admin-only actions (rename the family, delete a baby, remove a member) and instance-admin-only actions (02) are enforced by the API, not only hidden in the UI.

## Data

- **Family:** id, name, created at, created by user.
- **Membership:** family, user, role (admin / member), joined at. Unique per family and user; one admin per family (unique partial index). Deleted with its family; deleted with the user's account.
- **Baby:** id, family, name, birth date (date only, no time), sex, birth weight g (nullable), birth length cm (nullable, one decimal), birth head circumference cm (nullable, one decimal), created at, created by user, updated at.
- Birth measurements live on the baby. Growth (10) shows them as the first point of the growth history rather than duplicating them as entries.
- **Invitation:** as defined in 02, plus `revoked at` and its family (join invitation) or none (new-family invitation).
- Deleting a baby cascades to every activity table's entries for that baby. Deleting a family cascades to its babies, memberships and invitations.

## UI notes

- Settings area with sections: Family, Babies, Members & invitations (all for the current family), Home sections (04), Account (02), Instance (02, instance admin only), Appearance.
- Baby switcher: compact control in the top app bar showing the selected baby's name and age (or the current family's name without a baby); it opens a menu (`mat-menu`) listing each baby with their age, the selected one ticked, grouped under family names when the user has several families.
- Baby form, member list item and invitation list item are shared UI components.
- All text through i18n (EN/FR); ages and dates formatted in the user's language.

## Out of scope

- Family admin handover (feature list, idea); leaving a family on one's own (ask the family admin, or delete the account).
- Instance admin access to family data; moving a baby to another family; merging families.
- Roles beyond member / family admin, read-only members.
- Baby photos.
- Per-baby access (a member sees all of their family's babies).
- Archiving a baby (only delete).
